Security model

A database leak should not become a secret leak.

Hierarkey encrypts each secret revision with its own data encryption key, wraps those keys per namespace, and keeps the root of trust outside the database.

Master Key root of trust
Namespace KEK limits namespace blast radius
Revision DEK unique per secret version
Encrypted secret AES-256-GCM
◇

Hierarchical namespaces

Model environments, teams, tenants, or apps as paths like /org/prod/team-alpha.

⌁

Precise RBAC

Roles, rules, bindings, wildcard matching, default deny, and deny-overrides-allow semantics.

↻

Safe rotation

Rewrap master keys, rotate namespace KEKs, and revise secrets without breaking consumers.

✓

Audit trail

Track actor, timestamp, operation, and outcome across the platform. Tamper-evident audit is commercial.

Workflow

Ship secrets like infrastructure, not tribal knowledge.

1

Create namespaces

Split production, staging, teams, and apps into clear security boundaries.

2

Bind access

Grant only the actions each account needs, scoped by namespace or secret path.

3

Store revisions

Add new secret versions, stage them, activate them, or roll back when needed.

4

Rotate keys

Reduce blast radius with KEK and master-key rotation without rewriting application code.
